# Развёртывание RAG-агента 1С и загрузка CF в Qdrant

## Быстрый старт (3 шага)

1. **Выгрузите конфигурацию в файлы** (вы делаете это сами):
   Конфигуратор → *Конфигурация → Выгрузить конфигурацию в файлы* → любая папка,
   например `D:\dumps\upp`. Нужны каталоги `Documents/`, `CommonModules/` и т.д. с `*.bsl` и `*.xml`.
2. **Запустите `deploy.bat`** (двойной клик). Он создаст `.venv`, поставит зависимости,
   создаст `.env`, поднимет Qdrant в Docker (если он есть) и откроет панель
   <http://127.0.0.1:8765>.
3. **В панели** (всё настраивается и запускается оттуда):
   - **«Выгрузка и нарезка»** → «Папка выгрузки конфигурации» (`D:\dumps\upp`);
   - **«Подключение к 1С»** → выберите режим (см. ниже), для `http` — адрес публикации и пользователь;
   - **«LLM для CLI»** → провайдер, модель, API-ключ;
   - **«Сохранить настройки»**;
   - **«Запуск и проверки»** → «Запустить индексацию» → «Проверить всё» → «Запустить MCP-сервер».

### Режим работы с 1С

| Значение «Подключение к 1С» | Что работает |
|---|---|
| `none` — **без 1С, только Qdrant** | поиск и чтение кода, список и поиск объектов (из каталога индекса), справка платформы. Запросы к данным базы, журнал и сеансы возвращают понятное «нет подключения к 1С» |
| `http` | всё выше + данные, запросы, отчёты через публикацию `hs/ai` |
| `com` | то же через COM (только Windows) |

Режим `none` нужен, если доступа к базе нет или нужен только анализ кода. Чтобы включить 1С позже,
смените значение в панели и перезапустите MCP-клиент.

### «Проверить всё»

Последовательно проверяет: зависимости → конфиг → папка выгрузки → пробная нарезка → Qdrant →
модель эмбеддингов (и совпадение размерности с коллекцией) → реальный поиск по коду → связь с 1С
(в режиме `none` пропускается) → LLM → сборка MCP-сервера (число tools). У каждой ошибки есть подсказка.
Кнопки «Установить зависимости», «Запустить Qdrant (Docker)» и «Запустить/Остановить MCP-сервер»
(HTTP, порт задаётся на вкладке «MCP-сервер», по умолчанию 8100) находятся там же.

Позже панель открывается через `panel.bat`.

## Что происходит при индексации

```
папка выгрузки ──prepare──► knowledge/qdrant_ready/config_chunks.jsonl ──index──► Qdrant (onec_code)
```

**Нарезка (автоматическая).** Каждый `.bsl` и каждый текстовый узел XML с запросом/кодом режется так:
- модуль ≤ «Размер чанка» — один чанк;
- больше — по границам `Процедура/Функция`, процедуры упаковываются в чанк до лимита;
  директивы (`&НаСервере`) и комментарии над процедурой остаются вместе с ней;
- процедура больше лимита — режется по строкам с перекрытием.

Каждый чанк получает контекстную шапку (класс метаданных, объект, расположение) и в Qdrant
дополняется `proc_names`, `callees`, `registers_written`, `form_name`, `module_role`.

**Инкрементальность.** ID чанка = путь + позиция, плюс `content_hash` текста. Повторный запуск
считает эмбеддинги **только для изменённых** чанков (остальные — «unchanged»). Поэтому после
повторной выгрузки CF достаточно нажать «Запустить индексацию» без галок.

## Когда нужны галки

| Ситуация | Галка |
|---|---|
| Сменили модель эмбеддингов или `passage_max_chars` | **Пересоздать коллекцию** |
| Из выгрузки удалили объекты/модули (в Qdrant остались старые) | **Пересоздать коллекцию** |
| Сменили размер чанка | **Пересоздать коллекцию** |
| Хотите принудительно пересчитать всё без удаления коллекции | Пересчитать все эмбеддинги |
| JSONL уже собран, нужно только залить | Без нарезки |
| Нужна справка платформы | Вместе со справкой платформы |

> **Важно (разовое).** Формат id чанков изменился (раньше в id входил кусок текста).
> Один раз выполните индексацию с галкой **«Пересоздать коллекцию»**, иначе в коллекции
> останутся дубли со старыми id. Это ~часы на большой CF; дальше — только инкрементально.

## Подбор размера чанка

Модель эмбеддингов по умолчанию (MiniLM) видит только **первые 128 токенов ≈ 500–600 символов** текста,
а в Qdrant чанк хранится целиком (его читает `read_code`, по нему же идёт лексический поиск).
Поэтому в текст для эмбеддинга добавляется **список всех процедур чанка** — семантика «знает» про
весь чанк, а не только про его начало. Формат помечен версией `EMBED_TEXT_VERSION` (в `content_hash`):
при смене формата инкрементальная индексация сама пересчитает векторы, пересоздавать коллекцию не нужно.

| Цель | Настройки |
|---|---|
| **По умолчанию (рекомендуется)** | чанк 2800, MiniLM, поиск `hybrid` |
| Точнее по смыслу тела | чанк 600–800 (чанков ≈ в 4 раза больше → индексация в разы дольше), пересоздать коллекцию |
| Длинное окно | модель с окном 512 токенов (например `intfloat/multilingual-e5-large`), чанк ≈ 1500; на CPU очень медленно; пересоздать коллекцию |

`passage_max_chars` > ~800 для MiniLM смысла не имеет. Меняете размер чанка, модель или
`passage_max_chars` → индексация с галкой «Пересоздать коллекцию».

## Подбор настроек под новую конфигурацию

Панель → «Запуск и проверки» → «Подбор настроек» (или `python scripts\tune_embedding.py --source D:\dumps\new_cf`).
Инструмент берёт выборку модулей, строит запросы из реальных процедур (имя словами и описание из комментария),
прогоняет модели × размеры чанка и показывает качество (recall@5, MRR), скорость и оценку времени
полной индексации. Рекомендация — самая быстрая комбинация в пределах бюджета времени, не хуже лучшей
больше чем на 5%. Результат: `exports/tune_embedding.json`; кнопка «Применить рекомендацию» пишет значения в `config.yaml`.

Порядок замены конфигурации: 1) выгрузить новую CF в папку; 2) указать папку в «Выгрузка и нарезка»;
3) «Подбор настроек» → «Применить рекомендацию»; 4) «Индексация» с галкой **«Пересоздать коллекцию»**
(старая индексация удаляется); 5) «Проверить всё».

Модели mpnet (~1 ГБ) и e5 (~2.2 ГБ) при первом использовании скачиваются с Hugging Face.
Оценка времени считается по `.bsl`; XML-запросы и формы добавляют чанков, реальное время больше на 10–30%.

## Хранилище Qdrant: только docker-том

`docker-compose.yml` хранит данные в именованном томе `rag_qdrant_vol`, **не** в папке Windows.
Причина: на Windows-папке, смонтированной в Docker (bind mount), векторы в Qdrant молча
превращались в нулевые (в тестовой установке 60–75% точек, исправленные возвращались в нули).
Поиск по смыслу при этом «работал», но возвращал случайные результаты; лексический поиск маскировал поломку.
На docker-томе проблема не воспроизводится (0 нулевых из 79 тысяч, в том числе после часа работы и массовых обновлений).

Не переключайте `volumes:` обратно на `./папка:/qdrant/storage`.

## Самопроверка и ремонт векторов

- Индексация сама проверяет эмбеддинги до записи и читает вектор обратно после записи.
- В конце индексации — полный скан на нулевые векторы; если нашлись, автоматически идёт ремонт (до 3 проходов).
  Если нули остались, индексация завершается ошибкой (код 1) и сообщает об этом.
- Отдельно: панель → «Запуск и проверки» → **«Починить векторы»** или
  `python scripts\index_qdrant.py --repair-vectors [--collection-code ИМЯ]`.
- Проверка **«Векторы (смысловой поиск)»** в «Проверить всё» краснеет, если векторы нулевые.
- Перенос коллекции между серверами без пересчёта эмбеддингов:
  `python scripts\qdrant_migrate.py --from URL --to URL --collection ИМЯ --to-collection ИМЯ`.

## Что индексируется и как чистится

| Что | Как |
|---|---|
| Модули `.bsl` | нарезка по процедурам, директивы и комментарии остаются с процедурой |
| Запросы из XML | `query`, `QueryText`, `expression` и т. п. |
| Карточки объектов | реквизиты, ТЧ, типы, синонимы, подписки на события, задания, подсистемы, константы |
| Карточки форм | события, реквизиты, команды с обработчиками, дерево элементов, ссылки на картинки |
| Карточки макетов | печатные формы (области, параметры, текст) и схемы компоновки (наборы, поля, параметры, варианты) |
| Не индексируется | сырой XML (xmlns, uuid, InternalInfo), раскладка форм «как есть», двоичное содержимое картинок |

Авто-чистка (универсальные правила, `config.yaml → prepare`): склейка дублей XML-источников (RLS-шаблоны ролей),
удаление декоративных разделителей и base64/uuid-блобов, отбрасывание пустых оболочек (только `#Область`/объявления).
Отчёт: `exports/prepare_report.json`.

Для вопросов про структуру («реквизит…», «команда формы…», «печатная форма…») поиск дополнительно ищет среди
карточек (маркеры — термины платформы, не имена объектов конфигурации). Для процедур в payload хранится
`proc_words` (имя процедуры словами), поэтому «получить курс валюты» находит `ПолучитьКурсВалюты`.

## Оценка качества поиска

Панель → «Запуск и проверки» → **«Оценить поиск»** или `python scripts\eval_search.py [--n 40] [--classes CommonModules,Documents]`.
Вопросы строятся из самой выгрузки, поэтому оценка работает на любой конфигурации. Результат на тестовой
выгрузке (79 тыс. точек, hybrid, hit@10): имя процедуры словами 0.96, описание 0.92, строка из тела 0.80
(правильный файл 0.96), структура объекта 0.96, макет 0.72, форма 0.52.

## Режимы ответа: программист / пользователь

Панель → «Агент» → «Для кого отвечает агент» (`agent.audience` в `config.yaml`):

| Значение | Поведение |
|---|---|
| `developer` | отвечает как коллега-программист: модули, процедуры, обработчики, пути; правки только как «Рекомендация (НЕ применено)» |
| `user` | простым языком, по шагам «где нажать», без кода и служебных имён; опирается на заголовки полей и команд из карточек форм |
| `both` | выбирает по вопросу |

Тексты режимов лежат в `knowledge/режим_программист.md` и `knowledge/режим_пользователь.md` — их можно править.
После смены режима перезапустите MCP-клиент.

## Подключение другой конфигурации

Панель → «Запуск и проверки» → блок «Подключить другую конфигурацию» или
`python scripts\onboard_config.py --source D:\dumps\upp14 --name upp14 [--limit 400] [--activate]`.

Новая выгрузка идёт в **отдельную** коллекцию `onec_code_<имя>`, рабочая не затрагивается:
нарезка с чисткой → индексация с проверкой векторов → замер качества на вопросах, построенных из этой выгрузки.
Итог: `exports/onboard_<имя>.json` и `exports/eval_<имя>.json`. С `--activate` после успеха переключаются
коллекция, папка выгрузки и каталог имён объектов в `config.yaml`; затем перезапустите MCP.
`--limit N` индексирует только первые N файлов (быстрая проба на 2–3 минуты, оценка берёт только проиндексированное).

Замер строится из самой выгрузки и не знает имён конкретной конфигурации, поэтому годится для любой (УТ, УПП, ERP, БП, своя).
Если качество по какому-то типу вопросов низкое — смотрите `misses` в `exports/eval_<имя>.json`.

```powershell
.\.venv\Scripts\python.exe scripts\full_qdrant_pipeline.py --code-only        # prepare + index (инкрементально)
.\.venv\Scripts\python.exe scripts\full_qdrant_pipeline.py --recreate         # с нуля
.\.venv\Scripts\python.exe scripts\prepare_config_for_qdrant.py --source D:\dumps\upp
.\.venv\Scripts\python.exe scripts\index_qdrant.py --code-only [--recreate | --full]
.\.venv\Scripts\python.exe scripts\index_qdrant.py --status
```

## Подключение MCP-клиента

Панель → «Первый запуск», шаг 4 показывает готовый JSON. Либо укажите клиенту
`command = <папка>\mcp.bat`. После смены настроек перезапустите MCP-клиент.

## Что где настраивается

| Вкладка панели | Файл |
|---|---|
| Подключение к 1С, Выгрузка и нарезка, Хранилище индекса (Qdrant), Модель поиска, Расчёт векторов, LLM для CLI, Агент | `config.yaml` (комментарии сохраняются; перед записью копия `config.yaml.bak`) |
| Поля-секреты (пароль 1С, API-ключи) | `.env` (в панели не отображаются; пустое поле = «не менять») |

Панель слушает только `127.0.0.1`, запись — только с заголовком `X-Panel`, редактируются лишь
перечисленные в панели ключи.

## Частые проблемы

| Симптом | Решение |
|---|---|
| `deploy.bat`: Python не найден | Установить Python 3.10+ с «Add to PATH» |
| Qdrant: ошибка соединения | `docker compose up -d qdrant` или в панели режим `local` |
| «Проверить папку выгрузки» — `ok: false` | Неверный путь или выгружен не тот формат (нужны `.bsl`/`.xml`) |
| Мало результатов поиска | Не завершилась индексация; смотрите вывод в панели, `--status` |
| Индексация остановлена на середине | Запустите снова — готовые чанки пропустятся |
